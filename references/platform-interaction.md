# 플랫폼별 조작과 화면 가장자리

레이아웃을 시작할 때 실제로 시스템이 차지하는 영역, 입력 수단, 스크롤 영역을 표시한다. 기존 앱의 프레임워크와 플랫폼 관습을 우선한다. 아래에서 변경이 닿는 부분을 골라 설계와 검수에 쓴다.

## 버튼

- 버튼은 행동을 일으키는 대상이나 결과 요약 근처에 둔다. 웹에서는 이동을 링크, 실행을 버튼에 맡기고, 켜짐·선택은 알맞은 상태가 드러나는 기본 조작을 쓴다. 주 행동의 위치와 위계는 작업 맥락을 따른다. 아이콘만 있는 조작은 접근 가능한 이름을 주고, 의미가 생소하면 보이는 이름을 함께 둔다.
- 눈에 보이는 아이콘 크기와 실제 누를 수 있는 크기를 따로 설계한다. 터치 영역이 이웃 버튼이나 시스템 제스처와 겹치는지 확인한다. Apple 지침의 일반 기준은 44×44pt, Android 터치 권장은 48×48dp다. 웹에서 WCAG 2.2 AA를 평가할 때는 24×24 CSS px과 간격 등 예외를 함께 확인한다. 단위와 기준을 구분한다.
- 터치로 바로 눌러 보고, 포인터로는 호버와 눌림, 키보드로는 초점 표시와 기본 동작을 확인한다. 대기 중에는 실행 대상과 결과를 읽을 수 있게 두고, 중복 실행이 문제가 되는 행동은 요청이 끝날 때까지 막는다. 비활성 이유가 다음 행동을 결정한다면 버튼 밖에서도 보이게 한다.

## 스크롤바와 스크롤

- 각 방향의 주 스크롤 영역을 정한다. 표·지도·타임라인처럼 별도 축이 필요한 경우에만 내부 영역을 나누고, 마우스 휠·트랙패드·터치·키보드가 어느 영역을 움직이는지 확인한다. 마지막 행·버튼까지 도달하고, 상세에서 돌아올 때 가능한 범위에서 스크롤과 선택을 복원한다.
- 기본 스크롤바와 사용자의 항상 표시 설정을 살린다. 오버레이형은 끝 열이나 조작을 덮을 수 있고, 공간을 차지하는 스크롤바는 나타날 때 열 너비를 바꿀 수 있다. 웹의 `scrollbar-gutter: stable`은 공간을 차지하는 스크롤바의 너비 변화가 문제일 때 고려한다. 오버레이형, 고대비, 좁은 폭에서도 가로로 더 볼 내용과 마지막 조작이 드러나는지 살핀다.
- 모바일에서 관성·탄성 스크롤, 당겨 새로고침, 가장자리 탐색은 지원되는 플랫폼 기본 동작을 먼저 쓴다. 내부 패널에서 부모 영역까지 스크롤이 넘는 문제가 있을 때 해당 축과 컨테이너를 조정한다. 웹의 `overscroll-behavior: contain`은 해당 영역 밖으로 스크롤이나 탐색 동작이 이어지는 것을 막으면서 지원되는 로컬 경계 효과를 보존한다. `none`은 로컬 효과도 막는다. 상위 화면의 뒤로 가기나 새로고침까지 끊기지 않는지 실제 환경에서 확인한다.

## 모바일 세이프 에어리어와 키보드

- 배경은 화면 끝까지 이어질 수 있다. 읽어야 하는 정보, 하단 버튼, 입력창, 시트와 닫기 조작은 노치·상태바·홈 인디케이터·시스템 내비게이션을 고려한 안전 영역에 둔다. 가로 회전 시 좌우 영역과 뒤로 가기 같은 가장자리 제스처도 확인한다. 시스템 UI 아이콘은 뒤의 배경과 구별되어야 한다.
- 네이티브는 플랫폼의 safe area 또는 window insets를 사용한다. 웹에서 전체 화면 끝까지 확장할 때는 `viewport-fit=cover`와 `env(safe-area-inset-*, 0px)`가 적용되는 가장자리를 함께 설계한다. 안전 영역을 부모와 같은 영역의 자식 양쪽에서 중복 계산하는지 확인한다. 기본 레이아웃 여백과 시스템이 필요한 여백을 구분한다.
- 키보드는 별도의 가림 영역이다. 키보드가 열렸을 때 입력값, 오류, 해당 행동에 계속 접근할 수 있는지 본다. 하단 고정 조작이 스크롤 내용 위에 겹치는 구조라면 마지막 항목과 포커스 표시가 드러나도록 실제로 덮는 높이만큼의 공간을 확보한다. 세로·가로, 키보드 열기·닫기, 모바일 웹 주소창 전환을 변경에 맞게 확인한다.

## 데스크톱 타이틀바와 창 제어

- 화면에서 **OS 창 제어·드래그 영역·앱 조작**의 자리를 각각 표시한다. macOS는 통상 왼쪽 위의 닫기·최소화·확대/전체 화면 시스템 버튼을 기준으로 한다. Windows는 일반적인 왼쪽에서 오른쪽으로 읽는 창의 오른쪽 위 캡션 버튼을 기준으로 하며, 오른쪽에서 왼쪽으로 읽는 창은 시스템이 계산한 배치를 따른다. 커스텀 프레임에서도 실제 시스템 또는 프레임워크가 제공하는 영역과 창 동작을 우선한다.
- 검색, 탭, 메뉴, 버튼의 입력 영역을 드래그 영역과 분리한다. 창 제목·탭이 길거나 창이 작아져도 시스템 버튼과 겹치지 않고 창을 잡아 옮길 자리가 있어야 한다. 활성·비활성, 최소 크기·최대화·전체 화면, 필요한 경우 화면 배율이나 RTL에서 확인한다. 창 닫기, 문서 닫기, 앱 종료는 각각 실제로 닫히는 대상을 기준으로 이름과 단축키를 정한다.
- 일반 브라우저 탭은 브라우저가 창을 관리한다. 설치형 웹 앱의 창 제어 오버레이를 지원할 때에는 현재 사용할 수 있는 타이틀바 영역을 기준으로 하고, 오버레이가 꺼졌을 때의 배치도 확인한다.

## 컨텍스트 메뉴·팝오버·보조 창

- 빠른 명령은 대상을 계속 볼 수 있는 자리에서 열린다. 화면 가장자리에서는 잘리지 않게 방향을 바꾸거나 위치를 옮긴다. 길고 입력이 많은 과업은 제목과 닫기 경로가 있는 시트나 보조 창으로 검토한다. 꼭 써야 하는 행동은 우클릭·길게 누르기 외에 알아볼 수 있는 경로도 둔다.
- 현재 대상, 다중 선택 범위, 닫히면 돌아갈 곳을 정한다. 메뉴는 해당 패턴의 키보드 조작을 따르고, 모달은 열린 동안 배경으로 포커스가 새지 않게 한다. 비모달 보조 창은 본문과 오갈 수 있게 한다. 닫기·Esc·플랫폼의 뒤로 가기 중 실제 지원되는 경로와 초점 복귀를 확인한다. 열었던 대상이 사라졌으면 다음으로 이어갈 수 있는 곳에 초점을 둔다.

## 스켈레톤과 로딩

- 첫 데이터를 기다리고 최종 구조를 예측할 수 있는 영역에만 스켈레톤을 검토한다. 실제 목록 행 높이, 이미지 비율과 너비에 맞춰 콘텐츠가 들어올 때 조작 위치가 튀지 않게 한다. 아직 로드되지 않은 자리는 조작 가능하게 보이지 않도록 하고, 실제로 읽을 수 있는 탐색과 내용은 유지한다.
- 빠른 처리에는 불필요하게 깜박이는 화면 전환을 피한다. 이미 내용을 보는 중 생긴 요청은 기존 내용을 유지할 수 있는지 먼저 살피고, 저장·갱신처럼 국소적인 요청은 해당 위치에서 상태를 알린다. 읽기 도구에는 대기 의미를 전달하고 장식용 자리표시는 탐색에서 제외한다. 움직임 줄이기에서는 정적인 자리표시를 쓴다.
- 완료·실패·확인된 빈 결과를 각각 보여준다. 스켈레톤이 끝난 뒤 실제 내용, 빈 상태 또는 알려진 오류가 나타나는지 확인한다. 쓸 수 있는 경우에만 다시 시도할 경로를 붙인다. 빠른 응답과 느린 응답, 실패, 다시 로드할 때의 위치와 초점을 확인한다.

## 검수 범위와 참고

화면 캡처는 위치와 가림을, 브라우저 조작은 해당 브라우저의 클릭·키보드·스크롤을 보여준다. 기기의 가장자리 제스처와 물리적 탄성, OS 창 버튼과 창 드래그는 그 플랫폼에서 조작해 확인한다. 대상 환경에 접근할 수 없으면 실제로 확보한 범위를 남긴다.

- 버튼과 초점은 [Apple 버튼](https://developer.apple.com/design/human-interface-guidelines/buttons), [Android 접근성 기본값](https://developer.android.com/develop/ui/compose/accessibility/api-defaults), [W3C 타깃 크기](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [W3C 초점 가림](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).
- 스크롤과 화면 가장자리는 [UIKit 탄성](https://developer.apple.com/documentation/uikit/uiscrollview/bounces), [CSS Overscroll](https://www.w3.org/TR/css-overscroll-1/), [CSS Overflow](https://www.w3.org/TR/css-overflow-3/#scrollbar-gutter-property), [Apple 레이아웃](https://developer.apple.com/design/human-interface-guidelines/layout), [웹 세이프 에어리어](https://webkit.org/blog/7929/designing-websites-for-iphone-x/), [Android 인셋](https://developer.android.com/develop/ui/compose/system/setup-e2e).
- 창과 문맥 UI는 [Apple 창](https://developer.apple.com/design/human-interface-guidelines/windows), [Windows 타이틀바](https://learn.microsoft.com/en-us/windows/apps/develop/title-bar), [설치형 웹 앱의 창 제어](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/how-to/window-controls-overlay), [Apple 컨텍스트 메뉴](https://developer.apple.com/design/human-interface-guidelines/context-menus), [WAI 메뉴 버튼](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/), [WAI 모달](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).
- 로딩은 [Carbon 로딩 패턴](https://www.carbondesignsystem.com/building-blocks/core/patterns/loading).
